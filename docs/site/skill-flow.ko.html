pi-oven — omp 플러그인 스킬 & 워크플로우 지도

oh-my-pi (omp) 위에서 네이티브로 동작하는 큐레이티드 워크플로우 + 규율 레이어의 단일 페이지 레퍼런스. 현재 릴리스 기준 SoT를 한국어로 압축한 읽기 전용 인덱스입니다.
24개 file-based agents 23개 skills 3개 commands · 1개 omp extension codex-first 릴리스 기본값

pi-oven 는 omp 의 플러그인입니다 (oh-my-pi, pi-coding-agent harness). 마켓플레이스 kzk 에 pi-oven@kzk 로 배포되며 현재 v0.2.1 입니다. 이 프로젝트는 omc, omo, Pocock, superpowers 에서 검증된 워크플로우를 흡수해, omp 네이티브 규율로 재구성합니다.

목표: omp 위에서 네이티브로 도는 최적의 에이전틱 워크플로우를 만드는 것. Claude Code 플러그인이 아니라 omp-first 런타임 레이어이며, 규칙의 정식 소스는 CLAUDE.md, agents/pi-oven-*.md, skills/<name>/SKILL.md, .omp/extensions/pi-oven.ts 입니다. 이 HTML 은 그 SoT를 빠르게 훑기 위한 파생 인덱스입니다.

이번 릴리스의 핵심 변화: PROFILE_A 가 codex-first 릴리스 기본값으로 고정되었고, 런타임은 native ask control plane과 dependency-ready task waves를 중심으로 정렬되었습니다. 즉, “어떤 모델을 쓸지”와 “언제 질문/승인/실행/검증이 이어지는지”가 모두 같은 흐름 안에서 정의됩니다.
읽는 방법: 새 기능/설계는 §5.1, 자율 실행은 §5.2, 모델 오버라이드/프로필은 §3, deep-interview/approval handoff 는 §6 brainstorming 과 §9 를 먼저 보면 됩니다.

2. 멘탈 모델

omp 는 에이전트, 스킬, 커맨드, extension 네 층으로 움직입니다. pi-oven 는 새 런타임을 덧붙이기보다, 이 네 층을 일관된 실행 규율로 묶습니다: 언제 스킬을 먼저 읽는지, 언제 질문을 멈추는지, 언제 서브에이전트로 쪼개는지, 언제 fresh verifier 가 닫는지까지를 명시합니다.

Agent24 files
file-based 서브에이전트 정의. frontmatter name: pi-oven:<role> (콜론), model: 배열, thinkingLevel, tools/blocked_tools, 본문 = 역할별 execution context.

위치 / SoT

  • 위치: agents/pi-oven-*.md
  • model/thinkingLevel 은 scripts/pi-oven-setup/profiles.ts 에서 파생
  • frontmatter 는 파생물, 본문은 hand-authored — 모델별 실행 규율의 실제 본체
Skill23 markdown
스킬은 description discovery 와 런타임 키워드 화이트리스트 두 경로로 활성화됩니다. 현재 런타임은 정확한 plugin-owned SKILL.md target 을 주입하며, 임의의 별칭을 허용하지 않습니다.

위치 / 성격

  • 위치: skills/<name>/SKILL.md (+ references/)
  • 본문은 English-only; 한국어는 키워드/사용자 대면 문서에만
  • 대표 흐름: brainstorming → spec-and-review → writing-plans → subagent-driven-development
Command3 templates
/pi-oven:<name> 형태의 명시 호출 표면. 커맨드는 설정/가시화/릴리스 경계를 제공하고, 실제 세션의 실행 규율은 여전히 런타임과 스킬이 결정합니다.

3개 커맨드

  • /pi-oven:setup — 모델 라우팅/프로필/프로젝트 스코프 설정
  • /pi-oven:doctor — 설치/환경/훅 상태 진단
  • /pi-oven:release — 버전·SoT·publish gate 릴리스 자동화

자율 실행은 커맨드가 아니라 autonomous-loop 키워드 트리거로 진입합니다.

Extension1 TS
런타임 강제 계층. load-time registry 검증, session_start 상태 hydrate, parent-only orchestrator conduct, native pi-oven_ask UI 를 담당합니다.

.omp/extensions/pi-oven.ts

  • validateAgentRegistry — provider/tool SoT 검증
  • session_start — 부모 모델 캡처 + deep-interview/approval 상태 재주입
  • pi-oven_ask — deep-interview / approval handoff 를 렌더하는 네이티브 single-select UI

3. 모델 라우팅 — 현재 릴리스 기본값

현재 pi-oven 의 핵심은 codex-first release default 입니다. 기본 배포 PROFILE_A 는 24개 전 역할을 OpenAI Codex 계열 primary 로 고정하고, B/C/D 프로필은 setup 시 opt-in override 로만 들어옵니다. 즉, 릴리스 SoT 는 단순해졌고, divergence 는 설정 레이어가 담당합니다.

핵심 원칙 — 모델은 frontmatter 가 아니라 override 체인으로 해석

omp 는 서브에이전트 모델을 task.agentModelOverrides 에서만 해석합니다. 키는 반드시 pi-oven:<role> 이고, frontmatter 는 릴리스 기본값일 뿐 최종 결정을 단독으로 내리지 않습니다.

pi-oven:role"] --> B["agent-file frontmatter
릴리스 기본값"]
  B --> C["글로벌 override
~/.omp/agent/config.yml"]
  C --> D["프로젝트 override
<cwd>/.omp/settings.json"]
  D --> E["runtime CLI flag"]
  E --> F["최종 모델 결정"]

  • 우선순위 (낮음→높음): agent-file model: < 글로벌 task.agentModelOverrides < 프로젝트 .omp/settings.json < runtime CLI flag
  • 프로젝트 레이어는 글로벌 위에 deep-merge 되며, record 는 키별 병합, 배열은 교체됩니다
  • 죽은 네임스페이스: 구 settings.pi-oven 는 제거됨 — per-role 모델 쓰기를 재도입하지 않습니다
  • 개인 override: /pi-oven:setup --override <role>=<model> → 글로벌 config 만 수정, 에이전트 파일은 그대로

PROFILE_A 모델 맵 (릴리스 기본값)

현재 SoT 는 CLAUDE.md 의 PROFILE_A 표입니다. 아래는 primary 모델 기준입니다.

모델thinkingLevel역할
openai-codex/gpt-5.5 high / xhigh executor, verifier, critic, planner, code-reviewer, debugger, test-engineer, security-reviewer, code-simplifier, tracer, analyst, architect, oracle, metis, deep-researcher
openai-codex/gpt-5.4 medium / high explorer, writer, designer, qa-tester, git-master, document-specialist, librarian, multimodal-looker, data-runner

프로필 B / C / D 의 의미

  • Profile B: codex-only override 를 명시적으로 config 에 써서 현재 설치를 강하게 pin
  • Profile C: all-Anthropic override (claude-opus-4-8 / claude-sonnet-4-6)
  • Profile D: OpenCode Zen only override (kimi-k2.6 / minimax-m2.5 / gemini-3-flash)
  • 네 프로필 모두 24개 전 역할 override 를 씁니다. Profile A 는 여기에 orchestrator Codex pair 까지 함께 refresh 합니다.
도구 SoT 도 함께 따라갑니다: tools: / blocked_tools 역시 scripts/pi-oven-setup/profiles.ts 가 SoT 입니다. 역할별 native tool 의무 사용(lsp, ast_grep, inspect_image, web_search, debug)은 frontmatter 가 아니라 이 SoT 체인과 extension 설정이 같이 강제합니다.
setup/help/runtime 경계: /pi-oven:setup, /pi-oven:setup --status, /pi-oven:doctor 는 상태를 보여주거나 저장할 뿐입니다. 실제 세션에서 어떤 질문을 던지고 어떤 스킬을 읽는지는 runtime conduct 와 persisted deep-interview / approvalFlow state 가 결정합니다.

4. 작업 유형별 가이드

현재 pi-oven 흐름은 “무조건 구현”이 아니라 승인 여부, 스코프 크기, 리스크, 자율 모드 여부 를 먼저 본 뒤 스킬을 연결합니다.

1. 작은 수정 / 단일 변화

문제와 목표가 명확하고, 설계 미결정이 없으며, 1–2 파일 수준

좋은 prompt

이 동작만 고쳐줘   이 문구만 갱신해줘

자동 로드 / 디스패치

code-quality-discipline 로 최소 수정 원칙을 확인하고, 코드 리스크가 커지면 large-task-delegation 으로 즉시 승격.

피하기

작은 변경인데도 spec/plan 체인을 불필요하게 여는 것.

2. 조사 우선 / read-heavy

5+ 파일 읽기, 호출부 전수 확인, 원인 미확정

좋은 prompt

전수조사해줘   호출부 다 찾아줘   코드베이스 조사

자동 로드 / 디스패치

codebase-survey → pi-oven:explorer. 외부 문서가 얽히면 pi-oven:document-specialist / pi-oven:librarian 를 추가합니다.

메인 역할

메인은 직접 5+ 파일을 읽지 않고, survey 결과를 받아 다음 스킬 입력으로 넘깁니다.

3. 새 기능 / 설계 변경

승인되지 않은 spec, 구조 변경, 사용자 결정이 남아 있음

좋은 prompt

기능 설계부터 하자 → spec 잡자 → plan 만들어

자동 로드 / 디스패치

codebase-survey → brainstorming → spec-and-review → writing-plans → subagent-driven-development

핵심 포인트

deep-interview 가 끝나기 전에는 구현 쓰기가 막혀 있고, approval handoff 는 pi-oven_ask 로 이어집니다.

4. 자율 실행

좋은 prompt

자율 실행   끝까지 끝내줘   ralph   autopilot

자동 로드 / 디스패치

autonomous-loop 가 먼저 들어오고, 필요하면 brainstorming 이 선행합니다. 이후 WORK-TYPE 에 따라 debugging / architecture / plan execution 으로 분기합니다.

메인 역할

ASK-FIRST 3-slot branch contract 수집, plugin-surface self-improvement 일 때는 exhaustive sweep 선행, 종료는 fresh-verifier 필수.

5. 버그 / flaky / 원인 조사

좋은 prompt

왜 깨지지   원인 찾아줘   flaky test

자동 로드 / 디스패치

systematic-debugging → 필요 시 deep-dive → fix 단계에서 tdd-strict → fresh-verifier

피하기

근본 원인 확정 전 증상만 덮는 수정.

6. 리팩토링 / 아키텍처 개선

좋은 prompt

리팩토링 기회 찾아줘   deepen modules

자동 로드 / 디스패치

improve-codebase-architecture 가 단일 진입점입니다. Step 0 에서 DRY 정리인지, 깊이 있는 구조 변경인지 구분한 뒤 서로 다른 경로로 보냅니다.

핵심 포인트

가벼운 정리는 pi-oven:code-simplifier, 깊은 변경은 survey + plan + 행동보존 검증이 붙습니다.

7. 리뷰 반영 / 커밋 경계

좋은 prompt

리뷰 피드백 반영   git commit   gh pr create

자동 로드 / 디스패치

receiving-code-review 로 코멘트를 검증한 뒤, 경계에서는 pre-commit-gate 와 필요 시 fresh-verifier heavy path 가 닫습니다.

피하기

리뷰 코멘트를 근거 없이 수용하거나, fresh evidence 없이 완료 선언하는 것.

메타 룰

  1. brainstorming 선행: 승인된 spec 이 없고 사용자 결정이 남아 있으면 구현보다 먼저 설계를 잠급니다.
  2. 5+ file read = survey 위임: 메인은 read-heavy 정찰을 직접 하지 않습니다.
  3. 3+ file edit / 200+ LoC = delegation-first: 구현은 fresh subagent wave 로 보냅니다.
  4. 코드 변경은 검증까지 포함: TDD / verifier / reverse-dep 확인 없이 “작동함”을 선언하지 않습니다.
  5. push 는 여전히 사용자 명시 승인: 자율 모드라도 자동 push 는 없습니다.

7. 3개 커맨드

omp 는 마켓플레이스 커맨드를 <plugin>:<file-basename> 로 네임스페이싱하므로, commands/*.md 파일명은 pi-oven- 접두사 없이 (setup.md → /pi-oven:setup) 여야 합니다. 자율 실행은 커맨드가 아니라 autonomous-loop 스킬 키워드로 진입합니다.

커맨드역할주요 인자
/pi-oven:setup agent 모델 라우팅 셋업 위저드 — Profile A (릴리스 기본), Profile B (openai-codex-only), Profile C (all-Anthropic), Profile D (opencode-zen-only). 메인 오케스트레이터 모델도 설정. --status · --reset · --import <file> · --apply --profile A|B|C|D · --validate smoke|full|none · --override <role>=<model> · --isolate | --no-isolate
/pi-oven:doctor 설치 헬스 진단 — 11-check 매트릭스 (omp version, bun, git, provider auth, MCP, skills, agents, state dir, eval runner, UC5 ops connector, memory/killer-tools). read-only, 설정 mutate 안 함. 인자 없음. pi-oven-doctor.ts 를 Bash 로 dispatch.
/pi-oven:release 안전한 릴리스 자동화 — version bump + 3-manifest SoT sync + changelog + publish gate. 기본은 안전 (--dry-run). --bump major|minor|patch | --version X.Y.Z · --from-tag vX.Y.Z · --dry-run · --publish · --update-changelog · --sync-label
doctor 의 11-check 중 check 4 (provider auth) · 5 (MCP) · 10 (UC5 credential) · 11 (memory/killer-tools) 은 환경/설정 이슈라 WARN 만 — 절대 FAIL 안 함. check 6/7/9 (skills/agents/eval-runner) 와 10-missing-skills 는 install-integrity FAIL. exit code 는 FAIL 만 반영 (WARN 은 acceptable).

9. Extension / hooks

markdown skill 은 선언만 할 수 있고 강제는 못 합니다. 현재 런타임 강제는 .omp/extensions/pi-oven.ts 와 그 하위 runtime 모듈이 담당합니다.

.omp/extensions/pi-oven.tsomp extension
load-time 검증, session_start hydrate, parent-only conduct 주입, native ask UI 등록을 맡는 단일 extension 입니다. label 은 pi-oven v0.2.1 으로 노출됩니다.

1. load-time 검증

  • validateAgentRegistry 가 agent model/provider/tool SoT 를 점검합니다.
  • agent file 의 model: 선언과 provider whitelist 가 어긋나면 load 단계에서 경고를 남기고, CI lint 가 hard gate 를 맡습니다.

2. session_start hydrate

  • 부모 세션 모델을 캡처하고, setup 상태와 discipline rule 을 재주입합니다.
  • persisted deepInterview 와 approvalFlow state 를 읽어 질문/승인 흐름을 재개합니다.

3. parent-only orchestrator conduct

  • dedup key pi-oven:orchestrator-conduct@v2 로 부모 세션에만 상시 conduct 블록을 주입합니다.
  • Interactive mode: SKILL-FIRST + WAIT-FOR-USER + ASK-WHEN-AMBIGUOUS.
  • Autonomous mode: SKILL-FIRST 만 유지하고 WAIT/ASK 는 boundary contract 로 대체합니다.

4. keyword routing + native ask UI

  • 런타임은 shipped skill 을 정확한 plugin-owned SKILL.md target 으로 매핑합니다. 임의 별칭이나 외부 namespace 는 허용하지 않습니다.
  • pi-oven_ask 는 single-select UI 로 deep-interview / approval handoff 를 렌더합니다.
  • askAboutChoices 는 승인/라우팅 설명 요청용, other 는 자유 입력이 실제 유효한 다음 행동일 때만 켭니다.
sanctioned completion path: deep-interview 가 끝나면 최종 spec 을 저장하고 root approvalFlow 를 seed 합니다. 따라서 deepInterview.phase = "complete" 이후에도 approval 이 별도 상태로 남아 있을 수 있으며, 이것이 현재 sanctioned handoff 입니다.
