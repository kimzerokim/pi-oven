§1. 이번 결정이 기대는 근거

주의. 아래 내용은 이미 조사에서 확인된 사실과 아직 사용자가 선택해야 하는 정책 결정을 분리해서 보여줍니다. 사실 확인과 정책 승인 단계를 섞지 않습니다.
근거 영역 현재 확인된 사실 왜 결정이 필요한가
설치 토폴로지 runtime keyword loader와 doctor 일부가 여전히 process.cwd()를 plugin-owned 파일 탐색 기준으로 사용합니다. marketplace standalone 설치에서 pluginRoot와 projectRoot를 분리할지 먼저 정해야 합니다.
네임스페이스 계약 프롬프트/문서/런타임 가이드는 skill://pi-oven:<name>, pi-oven:<role>를 정식 경로로 밀고 있습니다. bare form을 계속 허용할지, pi-oven gate 기준에서는 차단할지 사용자가 정해야 합니다.
설정 라우팅 setup writer 자체는 대체로 명시적이며 file-write 레이어 테스트도 있습니다. 문제는 writer 의도보다 installed behavior 증명 범위입니다.
문서 정합성 setup/doctor 설명 중 현재 CLI와 깔끔하게 맞지 않는 흐름이 남아 있습니다. 이번 사이클이 docs-tightening인지 CLI expansion인지 먼저 정해야 spec가 흔들리지 않습니다.
워크플로우 규율 조사 결과는 이미 “evidence first, decision review second”가 맞다고 가리킵니다. plan을 spec freeze 전에 다시 만들지 않기 위한 저장소 규칙이 필요합니다.

§2. 사용자 결정 카드

입력 방법. 각 카드에는 현재 권장안이 미리 선택되어 있습니다. 동의하면 그대로 두고, 바꾸고 싶은 카드만 다른 옵션을 고르세요. 메모는 최종 요약에 함께 포함됩니다.
D1 권장안 있음 결정 필요

루트 소유권을 어디까지 명시적으로 나눌까

Standalone reliability의 핵심은 plugin-owned 자산과 user project 자산이 서로를 가장하지 않게 만드는 것입니다.

핵심 근거. 조사 결과, 일부 runtime/doctor 경로는 아직 process.cwd()를 plugin 파일 탐색 기준으로 사용합니다. 이 상태에선 깨끗한 사용자 프로젝트가 plugin 저장소처럼 취급될 수 있습니다.
D2 권장안 있음 결정 필요

Standalone 실패를 사용자에게 얼마나 드러낼까

keyword loading이나 plugin integrity 문제를 debug log에만 남기면 설치 신뢰성 문제를 사용자가 늦게 발견합니다.

핵심 근거. 현재 위험은 writer intent보다 end-to-end installed behavior에서 드러납니다. 따라서 실패 표면을 제품 신호로 올릴지 결정이 필요합니다.
D3 권장안 있음 결정 필요

bare skill / bare role 허용을 계속 둘까

문서와 conduct는 이미 namespaced form을 정식 경로로 취급합니다. 남은 질문은 gate와 dispatch도 같은 기준으로 맞출지입니다.

핵심 근거. 이름이 느슨하면 sibling surface와 충돌할 수 있고, auditability가 약해집니다. 반대로 전체 플랫폼 bare form을 전부 금지하는 건 범위가 큽니다.
D4 권장안 있음 결정 필요

project-scope 설정만 했는데 global tool flag가 빠져 있으면 어떻게 할까

project scope를 순수하게 유지할지, 편의상 global을 몰래 건드릴지에 따라 setup/status/doctor 메시지가 완전히 달라집니다.

핵심 근거. 현재 전역 tool enablement는 global setup에서만 강제됩니다. project-scope-only 사용자는 라우팅은 맞아도 필요한 도구 플래그가 비어 있을 수 있습니다.
D5 분기 결정 결정 필요

setup/doctor 문서 드리프트를 docs로 맞출까, CLI를 넓힐까

이 결정이 이번 사이클의 구현 범위를 가장 크게 바꿉니다. 그래서 spec freeze 전에 반드시 골라야 합니다.

핵심 근거. 조사 결과 일부 문서 흐름은 현재 CLI와 충돌합니다. 둘을 동시에 사실이라고 둘 수는 없습니다.
D6 권장안 있음 결정 필요

Standalone reliability를 완료라고 부르기 위한 최소 증거는 무엇인가

file-write 테스트만으로는 설치 토폴로지 신뢰성을 증명하지 못합니다. 완료 기준을 먼저 고정해야 plan이 얇아지지 않습니다.

핵심 근거. 조사 결과 가장 약한 부분은 installed-topology end-to-end proof입니다. 즉, repo-root 단위테스트보다 실제 설치 구조 검증이 더 중요합니다.

§3. 결정 후 바로 이어지는 저장소 순서

  1. 이 워크시트에서 사용자 결정 수집
  2. 승인된 결정만 docs/specs/2026-06-18-standalone-runtime-reliability.md에 동결
  3. spec 상태를 implementation-ready 또는 계속 decision-pending 중 하나로 명확히 표기
  4. spec freeze가 끝난 뒤에만 새 plan 작성
중요. 이번 사이클에서는 plan을 다시 만들지 않습니다. 이 워크시트와 spec가 먼저이며, 그 전 단계에서 나온 plan은 현재 권한이 없습니다.
