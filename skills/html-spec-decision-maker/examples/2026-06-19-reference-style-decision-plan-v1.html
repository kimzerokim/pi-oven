§1 — 일반화된 근거 요약

가정: 이 예시는 특정 실제 저장소가 아니라, 제품형 SaaS 워크스페이스의 API/문서/브랜치 전략을 재정렬하는 가상 코드베이스를 대상으로 합니다.
  • API surface가 resource 중심에서 view/workspace 중심으로 이동 중입니다.
  • 문서 SoT가 hand-written spec에서 live OpenAPI로 이동 중입니다.
  • 주석은 많지만 실제 stale 비율은 낮고, 일부 주석은 테스트/빌드/스펙 산출에 영향을 줍니다.
  • 브랜치 기능은 이미 존재하지만 merge 기준과 신규 행 전파 정책이 불완전합니다.

DP-D9 브랜치 전략 (fork·merge·lock 스코프) 현재 선택: a=i · b=i · c=i

브랜치 관련 전략을 결정 가능한 형태로 정리합니다. view×branch, recordId 보존, merge 기준이 모두 연결되어 있으므로 세 축을 한 묶음으로 봅니다.

배경 사실 6건 (evidence 포함)
  • fork = background worker 의 rows+cells eager copy. 현재 public id 는 일부 재생성됨.
    evidence: branch-copy.worker.ts:148-204
  • merge = cell-level apply. parent branch 대상 매핑이 있는 행에만 브랜치 셀을 적용.
    evidence: merge.service.ts:61,69,183-208
  • 매핑 없는 신규 행은 apply 루프에서 skip — 브랜치에서 만든 신규 리소스가 parent 로 전파되지 않음.
  • main 브랜치 보호는 존재. archive 불가.
  • lock 은 workspace 전역으로 적용됨.
  • WS room 은 workspace:{workspaceId}:{branchId} 로 브랜치별 채널은 이미 분리.

D9-c parent INSERT 필드 시맨틱 (확정 후보): 브랜치 신규 행을 merge 시 target(parent) branch 에 INSERT 할 때 record_id 는 branch 행 값 보존, position 은 branch 행의 fractional position 값을 복사, version 은 parent 기준 신규 행으로 1 발급합니다.
결합 관계 (D6·D9-b·D9-c): public id 보존 + record_id merge 매칭 + 신규 행 전파는 한 묶음이 자연스럽습니다. 반대로 id 재생성을 유지하면 D9-b 는 자동으로 lineage 유지가 됩니다.
