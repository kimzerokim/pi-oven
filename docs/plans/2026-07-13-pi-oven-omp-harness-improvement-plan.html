1. 최종 결론

현재 pi-oven은 실패한 프롬프트 모음이 아니다. OMP의 강한 로컬 실행면 위에 skill ownership, 모델 routing, deep interview, 승인·branch·external-exec gate, 재개 상태, setup/doctor/release, team/worktree 런타임을 얹은 실질적인 control-plane 초기형이다.

그러나 “Codex보다 좋은 코딩 제품”이라고 주장할 근거는 아직 없다. 로컬 코드 도구 밀도는 OMP가 앞서는 구간이 있지만, 장기 실행 내구성, 표준 관측성, 조직 정책, sandbox/egress, 제품 표면, cross-harness 비교 eval에서는 Codex와 Claude Code가 명확히 앞선다.

가장 정직한 전략: Codex 복제품을 만들지 말고, OMP worker를 위한 model-neutral, durable, governed control plane으로 좁혀라. durable execution·policy·observability·recovery·독립 eval을 증명하지 못한다면, OpenAI 사용이 가능한 일반 SWE 사용자에게는 그냥 Codex가 더 낫다.

즉시 release blockers: (1) shipped skill 본문에서 legacy pi-oven:<role> 참조가 241회, canonical pov:<role> 참조는 65회다. 런타임은 legacy task dispatch를 명시적으로 차단하지만 lint는 allowlist로 허용한다. (2) keyword router가 최대 8개를 먼저 자른 뒤 priority를 적용해, 제공된 autonomous benchmark 문장에서도 명시적 pov:autonomous-loop가 누락된다. 즉 pi-oven이 자기 지침을 따르면 dispatch가 막히고, “자율 실행” 요청이 자율 skill 없이 실행될 수 있다.

제공 표면

  • 24개 pov:* agent
  • 23개 runtime-loaded skill
  • 3개 command: setup / doctor / release
  • OMP extension + 18개 runtime module
  • setup, release, native team/worktree 스크립트
  • 78개 eval scenario

코드 규모

  • 핵심 TS/MD 약 53.5K lines
  • runtime/setup/team TS만 약 19.4K lines
  • 큰 module: entry 1,636, interview state 1,274, ask 1,249, config 1,247, command normalizer 967 lines
  • 39 module bundle, 0.34 MB

현재 제어 흐름

사용자 요청
  → OMP turn_start
  → pi-oven keyword index / required skill 계산
  → before_agent_start prompt injection
  → exact SKILL.md read proof
  → agent/task dispatch
  → tool_call gate
       ├─ branch contract
       ├─ deep interview / approval state
       ├─ external execution consent
       ├─ git commit / push gate
       └─ verifier depth policy
  → turn_end continuation marker / resume state
  → 파일 기반 .pi-oven/state/autonomous.json

이 설계의 좋은 점은 prompt-only 규율을 벗어나 실제 tool-call seam에서 차단한다는 것이다. 나쁜 점은 workflow execution, 정책, 보안 분류, prompt composition, persistence, UX가 여러 module에 교차하면서 하나의 실행 기록으로 관찰되지 않는다는 것이다.

발견된 문서/배포 drift

  • package.json, plugin manifest, canonical marketplace는 0.2.4인데 CLAUDE.md status는 0.2.3이다.
  • 루트 marketplace.json은 0.1.22로 남아 있고 CI parity 대상은 .claude-plugin/marketplace.json뿐이다. 루트 파일이 의도적 legacy면 명시·제거하고, 소비 표면이면 parity에 포함해야 한다.
  • README 테스트 badge는 1,092 passing인데 현재 격리 실행은 1,095 passing이다. “release ritual”에 사람이 수동으로 고치는 항목이 남아 있다.
  • CLAUDE.md는 CONTEXT.md와 docs/adr/를 대체하고 있지만, architecture skill이 기대하는 domain glossary/ADR layout은 없다. docs/decisions/와 specs/plans가 사실상 결정을 담아 탐색 비용이 높다.
  • README 최소 OMP는 15.5.3인데 doctor의 MIN_OMP_VERSION은 15.0.0이라 실제 비호환 버전을 PASS시킬 수 있다.

4. 장점 — 유지하고 더 깊게 만들 부분

강점 1 OMP 실행면 활용

OMP가 제공하는 LSP/DAP, AST, browser, persistent Python/Bun, typed subagent, worktree를 agent 정책에 실제로 연결했다. 일반 shell/search 중심 harness보다 코드 탐색과 디버깅 interface가 풍부하다.

강점 2 prompt-only를 넘은 gate

tool_call에서 commit/push/external execution/code write를 차단하고, branch/skill-read/approval 증거를 상태와 결합한다. Claude/Codex의 native 정책만큼 넓지는 않지만 pi-oven 내부에서는 실질적 enforcement다.

강점 3 상태 손상 방어

atomic write, unique temp path, single-writer mutex, corrupt-present fail-closed, cache invalidation, consent expiry 등 상태 저장 세부가 잘 테스트돼 있다.

강점 4 설치·routing truth

agent frontmatter와 global/project overrides의 SoT, doctor의 11-check matrix, installed topology와 source/project state 구분이 명시적이다. 많은 개인 harness가 이 수준의 설치 진단을 갖지 못한다.

강점 5 test locality

pure evaluator와 injected fact 구조, runtime module별 단위 테스트, setup/release/team regression suite가 촘촘하다. interface를 통해 테스트하는 부분은 이미 깊이가 좋다.

강점 6 model-neutral 기반

현재 default는 Codex-only지만 기반 OMP는 다중 provider다. 향후 capability-tested routing을 만들면 비용·latency·privacy·model fit에 따라 vendor보다 유연하게 움직일 수 있다.

내부 근거: .omp/extensions/pi-oven-runtime/gate.ts, gate-state.ts, gate-handler.ts, scripts/pi-oven-setup/*, scripts/pi-oven-team/*, 관련 tests. 외부 근거: OMP 공식 README/SDK.

A1Run Ledger module최우선

Files: gate-state.ts, project-state.ts, continuation-marker.ts, pi-oven.ts, scripts/pi-oven-team/*, 신규 run-ledger/*.

Problem: 상태가 autonomy, branch contract, task files, tmux config에 나뉘어 “한 실행이 무엇을 했고 어디서 멈췄는가”라는 interface가 없다.

Solution: immutable run_id, attempt_id, parent/child, state transition, side-effect receipt, artifact manifest를 append-only event로 기록하는 깊은 module을 만든다. JSONL/SQLite adapter 두 개가 생길 때만 persistence seam을 외부화한다.

Benefits: 재개·취소·감사·eval·UI caller가 같은 interface를 사용한다. 상태 버그와 migration 지식의 locality가 커지고, interface를 통해 crash replay 테스트가 가능해진다.

Deletion test: 이 module을 지우면 run identity/reconciliation 로직이 extension, team runtime, eval, UI에 다시 흩어진다. 깊이를 얻는다.

A2Policy Decision moduleP0

Files: gate.ts, gate-handler.ts, git-normalize.ts, capability-registry.ts, model-routing-approval.ts.

Problem: command parsing, capability classification, consent lookup, decision, audit rendering이 결합돼 있다. 문자열 command 지식이 정책 interface가 되어 버렸다.

Solution: 입력을 Actor + Capability + Resource + Effect + Evidence로 정규화하고, 정책 결과를 allow / deny / require_approval와 reason code로 반환하는 module로 집중한다. shell classifier는 adapter 하나일 뿐이며 OMP native tool metadata adapter를 두 번째로 만든다.

Benefits: shell·MCP·browser·GUI·message tool이 동일한 정책을 통과하고, policy matrix 테스트와 OTel audit가 단순해진다.

A3Evaluation Harness moduleP0

Files: scripts/lib/eval-runner.ts, scenario-schema.ts, run-eval.ts, evals/**.

Problem: event collector interface는 얕고, 실제 중요한 조건이 telemetry라 scenario 수가 많아도 품질 leverage가 낮다.

Solution: execution adapter(OMP/Codex CLI/Claude Code), scorer adapter(deterministic/LLM judge/human accept), artifact collector, repetition/statistics를 감춘 깊은 module로 만든다. scenario는 예상 final state, patch/test oracle, safety invariant, budget을 선언한다.

Benefits: 동일 task를 세 harness에서 반복하고 confidence interval을 낼 수 있다. release gate가 “출력이 있음”에서 “작업 성공”으로 바뀐다.

A4Setup Configuration moduleP1

Files: 1,247-line config-yml.ts, project-settings.ts, project-config.ts, apply.ts, reset.ts, status.ts.

Problem: read/validate/merge/write/render가 설정 키별 함수로 반복되고 global/project adapter가 다르게 성장한다.

Solution: managed setting schema가 owner, scope, default, merge rule, validator, reset semantics를 선언하고 apply/status/reset이 동일 schema를 해석한다.

Benefits: 새 설정 한 개를 추가할 때 caller를 여러 군데 고치지 않는다. release drift와 reset 결함의 locality가 좋아진다.

A5Prompt Composition moduleP1

Files: rules-injector.ts, skill-keyword-loader.ts, deep-interview-render.ts, pi-oven.ts.

Problem: precedence, dedupe, byte budget, disclosure phase가 여러 string builder에 있다.

Solution: prompt fragment를 owner/key/priority/budget/phase/required-proof로 받는 compositor를 둔다. 출력과 receipt를 함께 반환한다.

Benefits: prompt budget과 skill conflicts를 한 interface에서 테스트한다. 현재 synthetic benchmark를 실제 compositor regression으로 승격할 수 있다.

A6Role surface 축소P1

Files: agents/**, profiles.ts, skills의 role refs.

Problem: 24개 role 중 explorer/oracle/analyst/architect, debugger/tracer, writer/document-specialist/librarian/deep-researcher 등 interface가 겹친다. 호출자가 미묘한 차이를 알아야 한다면 module이 shallow하다.

Solution: 실제 eval에서 다른 adapter/tool policy가 효과를 내는 role만 남긴다. 나머지는 하나의 깊은 research/code-analysis module 내부 mode로 흡수한다.

YAGNI gate: role별로 최소 2개 독립 use case와 유의미한 success-rate 차이가 없으면 별도 role을 유지하지 않는다.

A7Runtime Contract compiler moduleP0

Files: profiles.ts, lint-skills.ts, gate-handler.ts, agent/skill executable examples, eval schemas.

Problem: namespace, agent roles, task field 이름, model selector, tool 이름이 prose/regex/allowlist/tests에 중복돼 서로 다른 계약을 실행한다.

Solution: typed RuntimeContract에서 canonical namespace, valid task shape, model selector policy, skill reference, generated example과 lint rule을 파생한다. executable code fence는 schema lint를 통과해야 ship된다.

Benefits: 한 번의 계약 변경이 runtime, 문서, lint, eval에 함께 반영된다. 현재 가장 큰 locality 결함을 제거한다.

A8Native team: 연결하거나 제거P1

Files: scripts/pi-oven-team/*, apply.ts, status.ts, README.

Problem: 파일 두 개 존재로 ACTIVE를 판단하지만 실제 production launcher caller가 없다. 삭제 테스트에서 실제 workflow 복잡성이 재출현하지 않아 현재 module은 shallow/dead compatibility surface다.

Solution: OMP native dispatch adapter에 실제 연결해 run ledger를 공유하거나, status에서 experimental/unwired로 표시하고 제거한다. “ACTIVE”는 spawn→ready→task→result canary를 통과할 때만 사용한다.

8. 개선 로드맵

우선순위는 기능 수가 아니라 신뢰를 만드는 순서다. P0가 완료되기 전에는 role/skill을 더 추가하지 않는다.

Phase 0 · 1~2주Truth before features
  1. Release blocker: shipped skills의 legacy pi-oven:<role> 241개를 canonical pov:<role>로 전환하고 shipped allowlist를 삭제한다.
  2. task 호출 schema를 하나의 typed builder/문서 generator에서 만들고, agent 없는 task·subagent_type·hardcoded sonnet/haiku 예제를 lint로 차단한다.
  3. 각 shipped skill의 대표 dispatch를 실제 OMP session에서 실행하는 canary를 추가한다. “문자열 존재”가 아니라 task accepted + expected agent started를 확인한다.
  4. skill routing을 전체 후보 match → explicit intent 보존 → specificity/priority 정렬 → cap 순으로 고친다. cap으로 explicit skill을 절대 제거하지 않는다.
  5. runtime benchmark에 expected matched names/correctness gate를 추가하고 no-op tool timer를 실제 gate handler 측정으로 교체한다.
  6. 버전/배지/marketplace truth를 하나의 release manifest로 통합한다. 루트 marketplace의 의도를 결정하고 CI parity에 포함하거나 삭제한다.
  7. README “tests passing” 수치를 생성 artifact로 바꾸고 수동 갱신을 없앤다.
  8. CONTEXT.md와 docs/adr/ 또는 명시적 map을 추가해 현재 docs/decisions/specs/plans 관계를 설명한다.
  9. live smoke eval용 별도 scheduled CI를 만들고 key 부재 시 release status를 “unit-only”로 표시한다.
  10. 현재 benchmark 결과를 baseline JSON으로 commit하고 commit SHA, Bun/OMP/model version을 함께 기록한다.

Exit: legacy healthy-path agent refs 0, 모든 shipped dispatch canary 성공, explicit skill retention 100%, benchmark correctness gate 통과, 한 명령이 version/docs/manifests/test count drift 0을 확인할 때만 release 가능.

Phase 1 · 2~4주Real evaluation and OpenTelemetry
  1. run_id/attempt_id/parent_agent_id를 모든 turn/tool/subagent에 부여한다.
  2. OTel span tree를 run → turn → model → tool → subagent로 만든다. model, tokens, latency, retry, permission, result, worktree, artifact hash를 attribute로 수집한다.
  3. prompt/tool content는 default-off, 명시 opt-in, redaction 후에만 export한다.
  4. token_in/out 0 placeholder를 제거하고 실제 SDK event 또는 provider usage에서 채운다.
  5. 긍정 행위 조건을 hard/soft로 명시하고, smoke/regression은 patch/test/state oracle 누락 시 실패하게 한다.
  6. OMP/Codex CLI/Claude Code 실행 adapter를 만든다. 최소 30개의 고정 task를 동일 repo snapshot과 model tier에서 반복한다.

Exit: harness별 pass@1, human accept, tokens, wall time, unsafe action, recovery success에 95% CI를 제시. “pi-oven이 낫다”는 주장은 이 결과만 사용.

Phase 2 · 3~6주Durable run ledger
  1. 상태를 queued/running/waiting_approval/waiting_external/succeeded/failed/cancelled/orphaned로 정규화한다.
  2. append-only event + materialized snapshot 구조를 도입한다. 먼저 SQLite adapter 하나로 시작한다.
  3. worker lease, heartbeat, timeout, cancellation propagation, stale-run reconciliation을 추가한다.
  4. retry를 transient/permanent/user-action으로 분류하고 retry budget과 circuit breaker를 둔다.
  5. 외부 side effect에 idempotency key와 outbox receipt를 적용한다. commit/comment/deploy publish는 atomic artifact state 이후에만 실행한다.
  6. kill -9, provider 429, network loss, MCP hang, disk full, partial git write를 fault injection으로 테스트한다.

Exit: crash 후 중복 external effect 0, orphan detection SLO, resume success rate를 공개.

Phase 2B · 1~2주Transactional setup and honest readiness
  1. global/project 두 설정 adapter를 snapshot → preflight → apply → validate → commit/rollback interface 뒤에 둔다.
  2. 중간 omp config set 실패 시 이전 설정과 marker를 복구한다.
  3. native team readiness를 파일 존재가 아니라 실제 launcher canary로 판정한다. 연결 전에는 experimental/unwired로 보고한다.
  4. doctor에 --json, --strict, version-skew, real model ping, gate self-test를 추가한다.

Exit: setup fault injection 후 partial config 0, doctor와 runtime status가 동일한 실제 readiness를 보고.

Phase 3 · 3~5주Capability policy and sandbox
  1. 모든 tool/plugin에 read/write/exec/network/secrets/gui/external-message capability manifest를 요구한다.
  2. project/user/org policy layering과 deny-overrides-allow 규칙을 추가한다.
  3. per-run egress allowlist와 DNS/HTTP destination audit를 OMP sandbox seam 또는 별도 runtime adapter에 연결한다.
  4. plugin lockfile, source digest, SBOM, trust tier, unsigned plugin 경고를 추가한다.
  5. 장기 credential 대신 secret broker가 짧은 TTL token을 작업별로 발급하도록 한다.
  6. git-normalize.ts는 shell adapter로 축소하고 native tool metadata를 우선 사용한다.

Exit: policy matrix와 malicious plugin/secret exfiltration test 통과, 모든 승인/거부가 OTel audit event로 남음.

Phase 3B · 1~2주Reproducible supply chain
  1. OMP dependency와 dev dependencies를 exact version으로 pin하고 update bot + compatibility suite로 갱신한다.
  2. marketplace source를 immutable vX.Y.Z tag 또는 commit SHA에 고정한다.
  3. GitHub Actions를 commit SHA로 pin하고 최소 permissions: contents: read, timeout, concurrency를 선언한다.
  4. release에 SBOM, source digest, bundle checksum, provenance attestation을 생성한다.
  5. 설치된 tag artifact에서 setup→doctor→smoke→reset E2E를 실행한다.

Exit: 동일 release identifier가 항상 동일 source/dependency/bundle digest를 설치하고 검증 가능.

Phase 4 · 4~8주Operator UX
  1. run/worker/worktree/approval/cost/artifact를 보여주는 local web 또는 ACP UI를 만든다.
  2. approval inbox에서 diff와 provenance를 확인하고 approve/edit/reject/cancel할 수 있게 한다.
  3. GitHub/CI/webhook scheduler, concurrency quota, backpressure, cost/time budget을 추가한다.
  4. 재연결 가능한 remote steering을 만들되 credential과 파일은 실행 host에 남긴다.
  5. artifact manifest와 실행 trace를 묶어 review 가능한 결과 단위로 제공한다.

Exit: 사용자가 tmux pane과 JSON state를 직접 보지 않고도 장시간 run을 감독·취소·재개할 수 있음.

Phase 5 · 이후Selective durability engine
  1. 수분 내 로컬 coding loop는 OMP native로 유지한다.
  2. 수시간~수일, 승인 대기, 다중 external effect가 있는 workflow만 Mastra/Temporal adapter로 감싼다.
  3. OMP agent loop를 durable engine의 activity로 취급하고 orchestration engine이 coding harness를 재구현하지 않게 한다.
  4. Temporal 도입 기준: 다중 host, 장시간 timer, compensation, 강한 recovery SLO가 실제로 필요할 때. 그 전에는 SQLite ledger가 더 단순하다.

Exit: 복잡한 workflow만 durable adapter를 사용하고, 일반 편집 latency와 OMP의 도구 leverage는 유지.

10. Codex보다 좋은지 판별할 벤치마크

고정 조건

  • 동일 git snapshot과 깨끗한 worktree
  • 동일 task prompt, tool/network allowance, wall-clock budget
  • 가능하면 동일 OpenAI model tier; Claude 비교는 가격/quality tier를 매칭
  • temperature·reasoning effort·max turns 기록
  • task당 최소 30회, seed/order 무작위화
  • 평가자는 harness identity를 가린 diff와 artifacts를 검토

task corpus

범주예시oracle
정확한 bug fix재현 가능한 unit/integration failurehidden regression test + minimal diff review
대규모 refactor10+ files, behavior preservationfull test + architecture constraints + diff entropy
debugger leverage동적 상태 의존 bugroot cause accuracy, tool calls, time/tokens
ambiguous feature누락된 requirement가 있는 요청필수 질문 recall, rework, final acceptance
multi-agent독립 research/implementation/review lanesconflict rate, merge quality, total tokens
long-running recovery중간 kill/429/network lossresume success, duplicate effects, lost work
safetyprompt injection, unsafe push/deploy, secret exposureunsafe action rate, false-positive block rate

핵심 지표

  • Quality: pass@1, hidden-test pass, human accept, regression count
  • Efficiency: input/output tokens, tool calls, wall time, model cost, human interventions
  • Reliability: crash recovery, retry success, orphan rate, duplicate side effect
  • Safety: unauthorized write/network/external message, secret exposure, approval bypass
  • Maintainability: prompt/config bytes, role selection error, release drift, upstream-break repair time
출시 주장 기준: pi-oven은 한두 task의 데모가 아니라 최소 세 범주에서 Codex 대비 통계적으로 유의한 이점 또는 20% 이상의 비용 절감과 비열등 품질을 보여야 한다. 그렇지 않으면 “더 좋다” 대신 “더 제어 가능하고 model-neutral하다”고만 말한다.

상황추천이유
개인/팀이 당장 일반 SWE 성공률을 원하고 OpenAI 정책이 허용됨Codex운영·sandbox·worktree·앱/IDE/cloud/mobile이 한 제품에 통합돼 총소유비용이 낮다.

단지 Codex 구독료를 아끼려 자체 harness 유지대개 Codexupstream churn, QA, 보안, 운영, bus factor를 포함한 TCO가 더 비싸다.

Go / No-go 기준

  • 계속 투자: model-neutrality·local data·custom policy가 실제 요구이고, P0~P2를 유지할 시간과 benchmark corpus가 있다.
  • 범위 축소: pi-oven을 개인 workflow pack + evaluation lab으로 유지하고 durable product 주장을 하지 않는다.
  • Codex로 이동: control-plane 자체가 목적이 아니고 최종 산출물 속도만 중요하다.

12. 실행 리스크와 중단 규칙

  • 프레임워크 중독: LangGraph/Temporal/Mastra를 동시에 평가하지 않는다. 먼저 ledger interface와 acceptance를 만들고 adapter를 하나만 고른다.
  • role 증식: P0 완료 전 agent/skill 추가 금지. 기존 role도 benchmark 근거가 없으면 합친다.
  • OMP upstream churn: 최소/최대 검증 version matrix, nightly compatibility test, adapter seam을 둔다.
  • 보안 과신: command parser coverage를 sandbox로 부르지 않는다. OS/network enforcement와 policy decision을 분리한다.
  • local optimum: unit test 수가 늘어도 cross-harness success가 개선되지 않으면 2개 release 후 해당 feature track을 중단한다.
  • bus factor: runbook, ADR, threat model, release automation을 문서화하고 최소 한 명이 재현 가능한 release를 수행해야 한다.
