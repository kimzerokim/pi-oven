승인된 결정

ID 승인안 최종 결정 근거 / 이유 즉시 구현 영향
D1 A pluginRoot, projectRoot, home 경계를 명시적으로 분리한다. survey들은 runtime keyword loader와 doctor 일부가 아직 process.cwd()에 기대어 plugin-owned 자산을 잘못 해석할 수 있음을 공통으로 지적했다. runtime/doctor/path resolution은 plugin-owned 자산을 project root에서 찾지 않도록 정리해야 한다.
D2 A keyword-index / plugin-integrity 문제는 visible warning으로 올리고, doctor/status가 같은 신호를 보여준다. clean install 리스크는 debug log에만 남기면 사용자가 늦게 발견한다. standalone 계약 위반은 operator-visible signal이 필요하다. runtime warning, /pi-oven:doctor, /pi-oven:setup --status의 truth surface를 맞춰야 한다.
D3 A pi-oven gate와 pi-oven-dispatched identity에서는 namespaced form만 정식 경로로 취급한다. namespaced guidance는 이미 강하지만, bare form이 gate credit나 dispatch 통과 경로로 남아 있으면 auditability와 sibling collision 방지가 약하다. skill://pi-oven:<name>, pi-oven:<role>만 pi-oven 성공 경로로 인정하도록 gate/runtime validation을 맞춘다.
D4 A project scope는 순수하게 유지하고, setup/status/doctor는 필요한 global remediation만 명시한다. project-scope routing이 숨은 global write로 확장되면 현재 경계 모델과 setup semantics가 무너진다. project-only 사용자는 부족한 global prerequisite를 명시적으로 안내받아야 하며, 자동 global write는 추가하지 않는다.
D5 A 문서 드리프트는 docs-tightening으로 해결한다. 현재 없는 CLI/runtime surface는 이번 사이클에서 약속하지 않는다. survey들은 setup/doctor/README 일부가 현재 실제 CLI와 충돌함을 지적했다. 이번 주제는 truthfulness 복구이지 CLI 확장 자체가 아니다. 지원하지 않는 명령 조합, validate path, 복구 경로는 문서에서 제거하거나 correction note로 정리한다.
D6 A installed-topology 테스트와 doctor/status evidence를 최소 완료 기준으로 채택한다. repo-root 단위테스트만으로는 standalone 설치 토폴로지 신뢰성을 증명할 수 없다는 점이 모든 조사에서 반복되었다. pluginRoot와 projectRoot가 분리된 시뮬레이션에서 테스트와 operator-facing evidence를 수집해야 완료를 주장할 수 있다.

이 결정 집합이 구현에 강제하는 것

  • root-boundary 수리와 installed-topology proof가 구현 우선순위의 맨 앞에 온다.
  • visible warning, doctor, status는 같은 계약을 다른 표면에서 반복해 보여줘야 한다.
  • pi-oven 전용 gate/dispatch identity는 namespaced form으로 닫힌다.
  • project-scope purity를 깨는 편의성 확장은 이번 계획 범위에서 제외된다.
  • 문서는 현재 실제 제품을 따라가야 하며, 문서에 맞추려고 새 CLI 동작을 약속하지 않는다.
