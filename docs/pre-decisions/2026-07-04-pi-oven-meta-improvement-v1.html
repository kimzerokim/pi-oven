DP-01 · Scope

딥 인터뷰 패리티를 어디까지 한 묶음으로 옮길 것인가

현재 pi-oven은 키워드 화이트리스트와 프롬프트 conduct 중심이라, 애매한 요청을 구조적으로 받아내는 typed interview primitive가 비어 있습니다. 이 공백을 어떤 마이그레이션 단위로 메울지에 따라 이후 state store, handoff, approval flow 설계가 달라집니다.

왜 중요하나

  • 너무 작게 옮기면 “질문은 더 친절해졌지만 상태·재개·handoff는 여전히 prompt 의존”인 반쪽 패리티가 됩니다.
  • 너무 크게 옮기면 gajae의 모놀리식 팀 런타임까지 들여오게 되어 pi-oven-first 원칙을 바로 훼손합니다.
  • 이 결정은 이후 ask API, state merge, approval-gated handoff를 runtime 계층에 둘지 skill 계층에 둘지까지 연쇄적으로 고정합니다.

판단 기준

  • 애매한 요청을 실제로 줄이는가
  • 내구성 있는 재개 / 상태 병합이 가능한가
  • pi-oven 고유 primitive로 소유 가능한가
  • 모놀리식 외부 런타임을 끌어오지 않는가

DP-02 · Cutover

OMC / superpowers 잔재를 어떤 경계에서 끊을 것인가

이번 재설계가 진짜 “pi-oven-first”가 되려면, 외부 하네스의 bootstrap 메시지 주입·tool remap·형식상 vendor 잔재를 단순히 감춘 채 유지할지, 아니면 pi-oven 네이티브 primitive로 경계를 재정의할지 먼저 결정해야 합니다.

왜 중요하나

  • 컷오버 전략은 이후 모든 기능 작업이 “새 구조 위”에서 진행되는지, “과거 구조를 우회”하며 진행되는지를 결정합니다.
  • requiredSkills, ownedSkillReadTargets, branch-contract, externalExecConsent 같은 제어면 계약은 이미 pi-oven 정체성의 중심부입니다. 여기에 OMC / superpowers 방식이 섞이면 원인 분석이 계속 흐려집니다.
  • 특히 sibling suppression과 claude-layer isolation이 우발적 설정인지, 명시적 정책인지 지금 분리해야 합니다.

판단 기준

  • dual plugin/runtime coupling을 줄이는가
  • bootstrap 메시지 / tool remap 같은 숨은 진입점을 제거하는가
  • pi-oven 고유 제어면을 선명하게 만드는가
  • 단기 이행 비용이 통제 가능한가

DP-03 · Parallel Runtime

병렬 런타임을 어디까지, 어떤 순서로 열 것인가

현재는 worker spawn / scale이 순차 루프여서 throughput 병목이 명확하지만, 병렬성은 곧바로 공격적으로 늘리는 순간 shared state와 write collision 문제가 같이 생깁니다. 이번 질문은 “병렬화 자체”보다 어떤 lane을 언제 병렬로 풀 수 있는가를 먼저 정하는 데 가깝습니다.

왜 중요하나

  • spawn/scale 병목만 고쳐도 속도는 일부 좋아지지만, lane 정책이 없으면 다시 prompt 레벨 암묵 상태에 의존하게 됩니다.
  • 반대로 너무 이른 전면 fan-out은 coding task 특유의 shared write-surface 문제를 키웁니다.
  • 계속성 표식(continuation marker)을 어디에 둘지도 같은 카드에서 결정해야 loop 재개와 병렬 orchestration이 충돌하지 않습니다.

판단 기준

  • 독립 lane과 공유 상태 lane을 명확히 구분하는가
  • 계속성 표식이 prompt 안이 아니라 파생 상태로 남는가
  • write-surface ownership이 명시되는가
  • scheduler refactor가 정책 뒤로 밀리지 않는가

  • end-state 아키텍처를 빠르게 검증할 수 있습니다.
단점
  • 병렬 정책, 상태 표식, 스케줄러 리팩터링이 한 덩어리로 얽혀 blast radius가 큽니다.
  • “코딩 작업은 덜 병렬화 가능”하다는 SOTA 경고를 거스르기 쉽습니다.
Option D

gajae / OMO 팀 런타임을 먼저 이식한다

병렬 실행 체감은 빠르게 얻지만 pi-oven 고유 정책은 뒤로 밀립니다.

장점
  • 이미 돌아가는 다중 세션 런타임을 참고하기 쉽습니다.
  • 표면상 동시성 기능은 빨리 보일 수 있습니다.
단점
  • ExternalHarnessCompare가 “gajae / OMO tmux-team 층은 첫 컷으로는 너무 무겁다”고 본 결론과 배치됩니다.
  • pi-oven의 control plane / write ownership 설계가 흐려집니다.

구현 방향

순서는 정책 → 표식 → 스케줄러가 되어야 합니다. 먼저 lane matrix와 write-surface ownership을 문서화하고, continuation marker를 prompt 내부 암시 상태가 아닌 파생 런타임 상태로 올린 뒤, 마지막에야 runtime-v2.ts / scaling.ts의 순차 로직을 교체하는 편이 안전합니다.

권고

Option B를 권합니다. 현 병목은 실제이지만, 병렬성의 핵심은 thread 수가 아니라 독립성 규약과 계속성 표식이기 때문입니다. 이 순서를 지켜야 이후 FSM 통합 여부도 더 정확히 판단할 수 있습니다.

DP-04 · Verification

검증 / 재검증 게이트를 얼마나 깊게 둘 것인가

메타 개선 플로우는 “끝났다고 착각하는 것”과 “멈춰야 할 때 못 멈추는 것”이 둘 다 위험합니다. 따라서 completion gate와 loop continuation gate를 어느 정도까지 분리하고, material edit 이후 재검증을 강제할지 정해야 합니다.

왜 중요하나

  • 현재 gate 변경은 단일 파일 수정이 아니라 gate.ts / gate-handler.ts와 autonomous-stop-guard.ts를 함께 보는 문제입니다.
  • 병렬 런타임과 deep-interview가 들어오면 “증거가 신선한가”, “질문 이후 재검증이 필요한가”를 별도 게이트로 다뤄야 합니다.
  • 검증을 너무 얕게 두면 메타 개선이 다시 prompt 낙관주의로 흐르고, 너무 깊게 두면 저위험 흐름까지 과도하게 느려집니다.

판단 기준

  • fresh evidence를 완료 직전까지 강제하는가
  • material edit 이후 재검증 규칙이 있는가
  • 모드별 hard cap / loop bounds가 정의되는가
  • 추적 surface가 raw prompt가 아니라 구조화된 상태에 남는가
Current gate topology

PiOvenSurvey는 verification 게이트가 gate.ts / gate-handler.ts와 autonomous-stop-guard.ts의 이중 구조라고 정리했습니다. 따라서 loop engineering이나 completion criteria를 건드릴 때 둘 중 하나만 수정하면 누수가 생깁니다.

Transferable rule

ExternalHarnessCompare는 superpowers의 /Users/kimzerokim/work/personal/external_harness/superpowers/skills/verification-before-completion/SKILL.md:1-48 에서 “fresh evidence before completion” 규율은 강하게 가져오되, bootstrap 메시지 방식은 가져오지 말아야 한다고 정리했습니다.

SOTA loop controls

SotaResearch는 OpenAI Runner의 max_turns, GitHub Copilot cloud agent의 59분 hard stop, Claude stop hook 계열의 블록 제한, Anthropic의 checkpoint / resume / tracing 요구를 함께 묶었습니다. 추가로, Debug2Fix와 ADI 계열 근거는 raw line-by-line debug보다 구조화된 trace surface가 효율적이라고 시사합니다.

옵션

Option A

현 게이트 구조를 유지하고 문구만 보강한다

리스크는 최소지만 재검증 규칙과 hard cap은 추가하지 않습니다.

장점
  • 구현이 가장 단순합니다.
  • 기존 흐름을 거의 깨지 않습니다.
단점
  • “완료 착각”과 “무한 루프”를 구조적으로 줄이지 못합니다.
  • 병렬 / 인터뷰 도입 후 필요한 revalidation 규칙이 없습니다.
Option B

fresh-evidence gate와 material-edit 재검증만 추가한다

완료 직전 검증과 변경 후 재확인 규칙을 우선 넣습니다.

장점
  • 현 구조를 크게 깨지 않고 실질 보호막을 추가할 수 있습니다.
  • completion 품질은 빠르게 좋아집니다.
단점
  • mode-specific hard cap과 loop bounds가 비어 있습니다.
  • 병렬 lane별 verifier depth 기준이 아직 없습니다.
Option C

모드별 hard cap + fresh evidence + 재검증 + verifier lane을 함께 둔다

completion gate와 continuation gate를 분리하고, 위험도 높은 흐름만 깊은 verifier를 붙입니다.

장점
  • loop bounds, 재검증, completion evidence를 한 번에 연결할 수 있습니다.
  • 저위험 흐름과 고위험 흐름의 검증 깊이를 분리해 과도한 slowdown을 피합니다.
  • future trace / debugger surface를 넣을 위치도 선명해집니다.
단점
  • 모드 분류와 위험 기준을 먼저 정의해야 합니다.
  • 정책 표면이 늘어 문서화가 중요해집니다.
Option D

모든 흐름에 heavy verifier를 강제한다

일관성은 높지만 낮은 위험 작업까지 과검증합니다.

장점
  • 실수 허용도가 가장 낮습니다.
  • 정책 설명은 단순합니다.
단점
  • 처리 시간이 과도하게 늘고 사용자 경험이 둔해집니다.
  • 검증 비용이 높은 흐름만 골라야 한다는 SOTA와 어긋납니다.

구현 방향

핵심은 검증을 “더 많이”가 아니라 “어디서 왜 멈추는지 분리”하는 것입니다. 즉, 완료 판정은 fresh evidence와 연결하고, 루프 지속 판정은 hard cap / checkpoint / continuation state와 연결하는 이중 게이트가 필요합니다. 이후 trace surface는 raw prompt 로그보다 구조화된 상태·함수 수준 단위에 가까워야 합니다.

권고

Option C가 가장 타당합니다. 현재 이중 게이트 구조를 활용하면서도, 병렬 런타임·딥 인터뷰 도입 후 필요한 재검증과 loop bounds를 함께 다룰 수 있는 유일한 선택지이기 때문입니다.
