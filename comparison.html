pi-oven은 omp 위에서 도는 플러그인이다. 그런데 omp가 박스에 내장한 18개 킬러 피쳐 — real debugger, arxiv PDF read, 14-프로바이더 web_search, Python/JS REPL, real browser, 큐레이션 메모리 — 를 pi-oven 에이전트 프롬프트는 거의 호출하지 못한다. 무엇이 가능/불가능하고, omp는 그걸 어떻게 트리거하며, 우리는 어디를 고쳐야 하는지를 한눈에 정리했다.

00TL;DR — 한 줄 결론

📌 두 시스템은 직교(orthogonal)한다

pi-oven의 강점 = 역할 전문화 + 모델 다양성. security-reviewer(OWASP·STRIDE), test-engineer(TDD), verifier, tracer, code-simplifier, metis, git-master 등 omp에 없는 전용 역할 다수. 22개 역할을 6모델·3프로바이더(anthropic·openai-codex·opencode-zen)에 정교하게 매핑.

omp의 강점 = 툴 능력(capability). 에이전트 수는 7개로 적지만, 그 에이전트들이 쥐는 30개 네이티브 툴 — debug(DAP), read(arxiv/PDF), web_search(14 backend), eval(REPL), browser(Chromium), retain/recall/reflect(메모리), irc — 이 압도적이다.

🎯 그래서 강화의 최대 레버는 "새 모델"이 아니라 "이미 깔린 omp 툴을 에이전트가 호출하게 만들기"

pi-oven 22 에이전트 중 omp의 킬러 툴(debug·eval·browser·read-URL· retain·irc·checkpoint)을 프롬프트에서 명시 활용하는 에이전트는 사실상 0개. 대부분은 코드 변경 없이 frontmatter 툴 allowlist + 프롬프트 한 문단만 고치면 즉시 켜진다.

01근본 원인 — 툴 이름이 어긋나 있다

omp의 빌트인 툴 registry는 전부 소문자 네이티브 이름이다. pi-oven 에이전트 frontmatter는 대문자 Claude Code 이름(Read/Grep/Glob/WebFetch)을 쓴다. omp 소스에서 둘을 잇는 자동 alias는 확인되지 않았다. 즉 web_search·debug·eval·browser·retain 같은 킬러 툴은 pi-oven 에이전트의 allowlist에 이름조차 올라가 있지 않다.

omp 네이티브 registry (30, 소문자)

read · bash · edit · ast_grep · ast_edit · debug · eval · ssh · github · find · search · lsp · inspect_image · browser · checkpoint · rewind · task · job · irc · todo_write · web_search · search_tool_bm25 · write · memory_edit · retain · recall · reflect · render_mermaid · ask

pi-oven 에이전트가 실제로 선언한 툴

거의 모든 read-only 역할: ["Read","Grep","Glob","Bash"] (+일부 WebFetch)
쓰기 역할: ["*"] (전부 허용이지만 프롬프트가 네이티브 킬러 툴을 언급하지 않음 → 안 씀)
blocked_tools: ["Write","Edit","apply_patch","task"]

⚠️ 두 가지 실패 모드

(A) 이름이 allowlist에 없다 — web_search/debug/eval/browser/retain은 Claude Code에 대응 이름이 없어, ["Read","Grep","Glob","Bash"]만 선언한 librarian·analyst·explorer 등은 이 툴을 받지도 못한다.

(B) 받아도 모른다 — debugger·qa-tester·executor는 ["*"]라 debug/browser/eval을 받기는 한다. 그런데 프롬프트가 "정적으로 코드 읽고 추론하라"고만 가르쳐서, 실제 디버거를 launch하거나 브라우저를 띄우는 동작을 한 번도 하지 않는다. ← 사용자가 지적한 "real debugger 못 쓴다"의 정체.

🧭 방향은 명확하다 — pi-oven은 omp 전용이다

CLAUDE.md가 못박듯 pi-oven은 omp 네이티브 워크플로우다 (Claude Code interop은 by-product, 유지 안 함). 따라서 Claude Code 툴명을 보존할 이유가 전혀 없다. 에이전트(22) · 스킬(21) · 커맨드 · 워크플로우의 모든 툴 참조를 Read/Grep/Glob/WebFetch/Bash → read/search/find/web_search/bash로 치환하고, 킬러 툴 (debug/eval/browser/retain/recall)을 역할별 allowlist에 올리는 전면 전환이 정공법이다. (전환 시 lint-agents/lint-skills 검증 규칙도 omp 네이티브 툴명 기준으로 함께 갱신 필요 — 스펙 단계 조사 항목.)

03omp는 킬러 피쳐를 "어떻게" 호출하나 (실제 문법)

사용자 질문 — "omp에서는 어떻게 킬러 피쳐 호출해서 쓰는지". 핵심은 두 가지다: (1) frontmatter tools:에 네이티브 툴명을 적어 활성화하고, (2) 툴 프롬프트(prompts/tools/*.md)가 호출 문법을 에이전트에게 주입한다. 예: omp librarian의 frontmatter는 tools: read, search, find, bash, lsp, web_search, ast_grep — pi-oven librarian의 ["Read","Grep","Glob","WebFetch","Bash"]와 대조적이다.

05OMP 빌트인 에이전트 7 — 적지만 강하다

omp는 에이전트를 얇게 가져간다. 능력의 대부분은 위 30개 툴에서 나오고, 에이전트는 그 툴을 어떤 순서로 쓰는지를 정의하는 얇은 셸이다. 내부 모델 별칭 pi/smol · pi/slow · pi/plan · pi/designer 사용.

explore pi/smol · med

  • 읽기전용 정찰. 타입 구조화 출력(summary/files/architecture)으로 핸드오프
  • 툴: read search find web_search — 정찰 에이전트조차 웹검색 보유
  • 한계: 쓰기·bash·lsp·subagent 불가

plan pi/plan+slow · high

  • 아키텍트. explore를 병렬 spawn해 종합 → 실행가능 계획
  • 툴: read/search/find/bash/lsp/web_search/ast_grep + task
  • 한계: 읽기전용(계획 문서만 산출)

librarian pi/smol · minimal

  • 외부 라이브러리 소스 직독. node_modules 우선, 없으면 git clone --depth 1
  • "소스가 진실, 문서는 희망, 학습데이터는 역사" — verbatim 인용 강제
  • 툴에 web_search·lsp·ast_grep 포함

oracle pi/slow · xhigh · blocking

  • 최강 단일 에이전트. consult(조언) + delegate(직접 구현) 듀얼 모드
  • 전체 툴 + explore spawn. 효과 추정 태그(Quick/Short/Medium/Large)
  • scope 규율: 시킨 것만, 관찰 최대 2개

reviewer pi/slow · high · blocking

  • cross-boundary 프로토콜: diff 밖이라도 새 타입의 소비측 dispatch 지점 추적
  • report_finding 전용 툴 → findings[] 기계추출. correct/incorrect 판정
  • bash 읽기전용(diff/log/show만)

designer pi/designer

  • anti-slop 미학 규율: glassmorphism·시안/보라 그라데이션·카드그리드 등 14개 금지 패턴 내장
  • 전체 툴(브라우저 라이브 검증 포함)
  • "어느 AI가 만들었나가 아니라 어떻게 만들었나를 묻게"

그 외 task/quick_task(범용 워커, 전체 툴), init(AGENTS.md 생성, explore 병렬 fan-out).

08🔥 pi-oven이 놓치는 omp 킬러 피쳐 — 에이전트별 매핑

"우리 에이전트가 omp 킬러 피쳐를 제대로 못 쓴다"의 구체적 증거. 각 행은 지금 무엇을 하는지 → omp 툴을 쓰면 무엇이 가능한지 → 고치는 난이도다.

09강화 후보 — 다음 단계 브레인스토밍용

사용자 로드맵: 이 HTML 확인 → 브레인스토밍으로 흡수 대상 선정 → 스펙·플랜 작성. 아래는 브레인스토밍에 올릴 후보 묶음이다. 결정은 다음 단계에서.

A. omp 네이티브 툴 전환 — 클로드코드 툴명 폐기 (최우선)

  • 전면 치환: 22 에이전트 + 21 스킬 + 커맨드/워크플로우의 Read/Grep/Glob/WebFetch/Bash → read/search/find/web_search/bash (frontmatter tools:/blocked_tools: + 본문 참조 모두)
  • 킬러 툴 allowlist 등재: 역할별 tools:에 debug/eval/browser/retain/recall 추가
  • 프롬프트 한 문단: 그 툴을 "언제·어떻게" 호출하는지 모델별 컨텍스트로 주입 (omp 툴 프롬프트 패턴 차용)
  • 대상: debugger→debug, analyst→eval, librarian/doc-spec→read-URL+web_search, qa→browser, looker→read-PDF
  • lint 갱신: lint-agents/lint-skills를 omp 네이티브 툴명 기준으로

B. 패턴 흡수 — omp 에이전트 설계 이식

  • report_finding 구조화: code-reviewer/critic 출력을 기계추출 가능한 findings[]로
  • cross-boundary 프로토콜: reviewer의 "diff 밖 소비측 dispatch 추적" 규칙
  • oracle dual-mode: consult/delegate 통합 검토
  • anti-slop 미학: omp designer의 14 금지패턴 → pi-oven designer 보강

C. 신규 역할 — 툴 주입으로 안 되는 갭

  • deep-researcher: web_search 14-backend + read-arxiv/PDF + (선택)Exa researcher 비동기 — 다중출처 적대검증 종합
  • data-runner: eval REPL 데이터 실행 역할 (또는 analyst 확장)

D. 인프라 — 설계 결정 필요

  • 메모리 정책: retain/recall을 로컬 상태 파일 대신/병행으로 쓸지
  • irc 협응: 병렬 dispatch 역할에 라이브 통신 도입 범위
  • checkpoint/rewind: 탐색계 역할(explorer/tracer)의 컨텍스트 압축
  • 모델 라우팅 유지: pi-oven 6모델 매핑은 omp 대비 우위 — 보존
